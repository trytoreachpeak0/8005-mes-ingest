# TOLL 前缀容量规则边界实验

## 目的

验证容量对照中的 `TOLL-` 前缀规则应匹配哪些 PACKAGE、不得匹配哪些值，以及精确规则与前缀规则冲突时的优先级。

## 关联问题

- `TOLL-8L(6R)`、`TOLL-11L(6R)` 等是否共享同一花篮容量。
- `TOLL`、`TOLL_`、前导空格、大小写变体或相似拼写是否应命中。
- 未来出现精确 TOLL 型号规则时如何覆盖通用前缀。

## 明确不回答

- 不决定具体容量数字，除非现场业务负责人提供批准证据。
- 不把字符串相似视为业务等价。
- 不自动修改正式容量参考。
- 不从单个活跃样本推断所有 TOLL 产品。

## 输入

- 已验证 evidence 中观察到的 PACKAGE 值。
- 经客户批准的 PACKAGE 全量发现实验候选集合（若有）。
- 当前容量对照版本。
- 业务负责人批准的正例、反例和容量结论。

## 前置条件与客户批准

- 输入样本具有 sourceEvidence 和哈希。
- 若需查询生产 MES，客户 IT 批准对象、时间、窗口和负载；否则仅离线执行。
- 业务负责人确认测试矩阵中的正例和反例，不由开发人员自行决定。

## 安全边界

- 保留原值用于证据；匹配前只允许正式规则已声明的 `strip()`，并明确记录归一化前后值，不改大小写或做 Unicode 归一化。
- 前缀匹配必须有明确分隔符边界，不使用无界模糊匹配或包含匹配。
- 任何新增规则先输出候选，不直接写入正式 reference。
- 不包含连接凭据或无关生产字段。

## 步骤

1. 固化输入 run、哈希、容量表版本和批准人。
2. 构造批准测试矩阵，至少包含：`TOLL-8L(6R)`、`TOLL-11L(6R)`、`TOLL-`、`TOLL`、`TOLL_8L`、`XTOLL-8L`、`toll-8l`、前后空格值、空值。
3. 按候选规则执行匹配并记录原值、是否命中、命中规则 ID 和容量。
4. 验证精确型号规则优先于通用前缀规则。
5. 验证非正例全部 fail-closed，不落入默认容量。
6. 对实际观察值运行同一规则，列出未决值和潜在误匹配。
7. 由业务负责人签署最终正例/反例边界后，才提出 reference 变更。

## 通过标准

- 所有批准正例按预期命中，所有批准反例均不命中。
- 每次命中能给出唯一规则 ID；规则冲突时精确规则优先。
- 只执行规则明确声明的 `strip()`，不做其他隐式归一化，也不把未知值分配默认容量。
- 结果可追溯到输入、规则版本和批准证据。

## 输出

- 正例/反例测试矩阵
- 实际观察值匹配报告
- 冲突与未决项
- 建议规则及业务批准记录
- manifest、日志和 SHA-256
